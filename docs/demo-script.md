# Сценарий демо — homelab-monitor

Хронометраж: **до 2 минут экранного времени** (CPU-инцидент ускоряется таймкодами
или показывается готовая запись ленты). Цель: показать разницу между сырым
алертом и алертом с AI-объяснением на одном и том же инциденте.

## Подготовка (до записи)

- [ ] `make up` — весь стек поднят, `docker compose ps` — все healthy
- [ ] `.env` заполнен (`GLM_API_KEY`; Telegram — опционально, без токена
      уведомления идут в консоль, alerts.log и веб-ленту)
- [ ] Открыты: веб-лента http://localhost:8081/ (главный кадр), Grafana
      http://localhost:3001, терминал
- [ ] `make cleanup` прогнан — прошлые воздействия убраны

## Хронометраж

### 0:00–0:15 — сетап

«Домашняя лаба: Prometheus собирает метрики, правила алертов настроены,
Alertmanager доставляет их агенту. Сейчас покажу, что происходит при инциденте —
сначала без объяснения, потом с ним.»

### 0:15–0:45 — часть 1: сырой алерт

1. `make incident-down` (стоп loki) — самый быстрый инцидент (~105 с до алерта).
2. Показываем Alertmanager UI (http://localhost:9093) / Prometheus alerts:
   `[CRITICAL] ServiceDown — Цель loki/loki:3100 не отвечает более 1 минуты`.
3. Показываем «разбор руками»: `docker compose ps`, `docker logs homelab-loki`,
   `curl -s localhost:3100/ready`. Комментируем таймер: «вот это я ищу причину сам».

### 0:45–1:30 — часть 2: алерт с объяснением

1. `make cleanup` (loki поднимется обратно), либо сразу `make incident-disk`
   (файл 9 ГБ, ~85–90 с до уведомления).
2. В веб-ленте появляется карточка: слева сырой алерт (лейблы, startsAt),
   справа — объяснение агента: **что случилось / вероятная причина / что
   проверить**, снизу — модель, латентность, метрики из Prometheus.
3. Читаем вслух: причина указана сразу («проблема локальна в корневой ФС,
   остальные разделы свободны», «load average 32 — похоже на CPU-нагрузку» и т.п.).

### 1:30–1:55 — итог

«Один и тот же инцидент: с сырым алертом разбор — минуты команд и догадок,
с объяснением — гипотеза уже в сообщении, остаётся проверить одной командой.
Данные и тайминги — в README, проект демо, цифры из локальных замеров.»

## Инциденты (Makefile)

| Команда | Алерт | Время до уведомления (замер) |
|---|---|---|
| `make incident-down` | ServiceDown (critical) | ~105 с |
| `make incident-disk` | HighDiskUsage (warning) | ~85–90 с |
| `make incident-cpu` | HighCPUUsage (warning) | ~10 мин (`for: 5m` + окно rate[5m]) |
| `make cleanup` | — | возвращает всё как было |

## Что фиксируем для замеров (демо)

| Замер | Сырой алерт | Алерт с объяснением |
|---|---|---|
| Время до формулировки гипотезы о причине (диск) | ~1,5–3 мин (каскад df→du→find ~13–15 с команд + ввод и интерпретация) | ~5–15 с (проверка одной командой из «что проверить») |
| Время инцидент → уведомление | — | 85–105 с (из них конвейер агента 11–15 с) |

## Чек-лист записи

- Таймер на экране или таймкод в монтаже
- Терминал крупным шрифтом; веб-ленту показать фуллскрином ≥ 3 секунд
- Не показывать `.env` и токены в кадре
